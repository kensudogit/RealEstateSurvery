# 03. LLM／AI-OCR による抽出（②）

実装は `scripts/extract_property.py` にある。まずそれを CLI で回して、
手元のマイソク PDF でどこまで取れるかを見てからサービス化する。

## OCR エンジンは原則いらない

Claude は PDF と画像をそのまま入力として受け取り、レイアウトを保ったまま
読み取れる。「OCR でテキスト化 → LLM で構造化」の 2 段構えにすると、
OCR が表の行列対応を壊した時点で情報が失われ、後段では復元できない。
販売図面のように**表と図が混在した文書ほど、画像のまま渡した方が精度が高い**。

例外は次の場合。

- ページ数が非常に多い資料（レントロール 100 ページなど）でコストを抑えたいとき
  → テキスト層があるページは `pdfplumber` で抜き、画像ページだけ Claude に回す
- 既に社内に AI-OCR の契約があり、そちらを使う要件があるとき
  → OCR 出力を「テキストブロック＋座標」の形で渡し、Claude に構造化させる

## 入力の組み立て

```python
content = [
    {"type": "document", "title": "mysoku.pdf",
     "source": {"type": "base64", "media_type": "application/pdf", "data": pdf_b64}},
    {"type": "text", "text": "[次の画像のファイル名: gaikan.jpg]"},
    {"type": "image",
     "source": {"type": "base64", "media_type": "image/jpeg", "data": img_b64}},
    {"type": "text", "text": "以下はメール本文です。…"},
]
```

- document / image はテキストより**前**に置く。
- 画像の直前にファイル名のテキストブロックを入れておくと、モデルが
  「どの画像がどれか」を指せるようになり、画像の用途分類（外観・間取り図・
  地図）が安定する。
- base64 は改行を含めない。リクエスト上限は 32MB、PDF は 600 ページ。
  添付が大きい場合は Files API（beta `files-api-2025-04-14`）にアップロードし、
  `{"type": "document", "source": {"type": "file", "file_id": ...}}` で参照する。
  同じ資料を再抽出するときに再アップロードが不要になる。

## 出力を JSON Schema で縛る

`output_config.format` に JSON Schema を渡すと、返ってくる最初の text ブロックが
必ずそのスキーマに適合した JSON になる。パースの防御コードが要らなくなる。

```python
response = client.messages.create(
    model="claude-opus-5",
    max_tokens=32000,
    system=[{"type": "text", "text": SYSTEM_PROMPT,
             "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": content}],
    thinking={"type": "adaptive"},
    output_config={"effort": "high",
                   "format": {"type": "json_schema", "schema": schema}},
)
```

スキーマは `assets/property_fields.json` から生成する（`build_schema()`）。
項目定義をコードに書き写すと、必ずどこかで食い違う。

長い添付を渡すときは `client.messages.stream(...)` + `get_final_message()` を使う。
非ストリーミングだと HTTP タイムアウトに当たることがある。

## envelope 形式にする理由

各項目を `{value, confidence, evidence}` で返させる。

- `value` … 読めなければ `null`。0 や空文字で埋めない
- `confidence` … 0.0–1.0 の自己申告
- `evidence` … 原文の該当文字列。**人間が検算するための材料**

`evidence` があると、レビュー画面で「モデルはここを見てこう判断した」を
そのまま表示できる。これが無いと、レビュー担当者は毎回 PDF を開いて
全項目を目で追うことになり、自動化した意味が薄れる。

## needs_review はコードで決める

モデルには出力させない。閾値も必須項目もあとから変わるため、判定を
モデル出力に埋め込むと変更のたびに再抽出が必要になる。

フラグを立てる条件:

1. 必須項目が `null`
2. `confidence` が閾値（既定 0.75）未満
3. 項目をまたいだ検算に引っかかった（`cross_check()`）

任意項目の単なる「値なし」ではフラグを立てない。全項目が要確認になると
フラグが情報を持たなくなり、人は見なくなる。

## 検算ルール

単発の項目だけ見ていると、単位の取り違えや桁ずれは confidence が高いまま
通り抜ける。`cross_check()` が最後の砦になる。

| ルール | 捕まえたいミス |
|---|---|
| 売買なのに価格が null | 抽出漏れ |
| 売買価格 < 100万円 | 「4,800万円」を 4800 と読んだ |
| 賃料 > 500万円/月 | 年額を月額欄に入れた |
| 表面利回りが 1〜30% の外 | 桁ずれ・別の数値の誤読 |
| 満室想定年収 ÷ 価格 と記載利回りの差が 0.5pt 超 | どれかが誤読 |
| 築年が 1900 未満／未来 | 和暦換算ミス |
| 面積が 1㎡未満／10万㎡超 | 坪と㎡の取り違え |
| 3LDK 以上で専有面積 40㎡未満 | 表の行列ずれ |

業務側と相談してルールを足していく。ここが充実するほど、人のレビュー時間が減る。

## プロンプトの要点

`scripts/extract_property.py` の `SYSTEM_PROMPT` が実物。設計意図は次のとおり。

- **推測禁止を理由込みで伝える。** 「間違った値は空欄よりはるかに有害」と
  書いてある。単に「推測するな」だけだと、モデルは親切心で埋めにくる。
- **単位の正規化ルールを具体例で示す。** 「4,800万円 → 48000000」まで書く。
- **図面固有のノイズを名指しする。** 手書きメモ、FAX ヘッダ、スタンプ。
  実際のマイソクにはこれらが必ず写っている。
- **表の行列ずれに注意を促す。** 販売図面の表は罫線が省略されていることが多く、
  ここが最頻出の誤読原因。
- **confidence の目安を段階で示す。** 目安が無いと全部 0.9 になる。

プロンプトを変えたら `prompt_version` を上げて DB に記録する。
これが無いと「先週より精度が落ちた」を追跡できない。

## コストを下げる

- **プロンプトキャッシュ** … システムプロンプト（スキーマ説明を含む）は毎回
  同じなので `cache_control: {"type": "ephemeral"}` を付ける。
  `usage.cache_read_input_tokens` が 0 のままならキャッシュが効いていない。
  1024 トークン未満の接頭辞は黙ってキャッシュされない点に注意。
- **Batch API** … 夜間にまとめて処理するなら `client.messages.batches.create()` で
  50% 安くなる。結果は投入順に返らないので `custom_id` で突き合わせる。
- **effort の調整** … 既定は `high`。単純なメール本文だけの案件は `medium` でも
  十分なことが多い。ゴールデンセットで精度差を測ってから下げる。

## 失敗時の扱い

`stop_reason == "refusal"` が返る可能性がある（HTTP は 200）。`content` を
読む前に必ず確認する。Opus 5 ではサーバサイドフォールバック
（beta `server-side-fallback-2026-07-01` + `fallbacks: "default"`）を
付けておくと、拒否カテゴリに応じて自動で別モデルに回る。

1 通に複数物件が入っているメールは、まず「何件入っているか」を判定する
軽い呼び出しを挟み、件数が 2 以上なら物件ごとに分割してから本抽出を回す。
1 回の呼び出しで複数件を配列で返させると、件数が増えるほど項目の取り違えが増える。
